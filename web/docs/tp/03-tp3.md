Ce TP légendaire est à réaliser en équipe de deux. Il compte pour **10%** de la note du cours.

Votre patron vous demande de développer un script PowerShell permettant de raconter de bonnes vieilles blagues de Chuck Norris afin d'augmenter la profitabilité de l'entreprise.

Vous devez utiliser l’API **ChuckNorris.io** (https://api.chucknorris.io/) pour générer les blagues. Cette API prend des requêtes GET et retourne du contenu JSON.

Vous devez développer le script et concevoir une **stratégie de test** pour vérifier sa conformité. Les exigences ci-dessous servent de référence pour la programmation et la conception des cas de test.

:::info Consignes de remise
La date limite pour la remise du travail est **le dimanche 29 novembre à 23h59**.

Vous devez remettre le script `Get-ChuckNorrisJoke.ps1` et le fichier Markdown `plan-de-test.md` à la racine du dépôt GitHub fourni par le professeur, avec un commit appelé **"Remise finale"**. [Voir ici pour les consignes détaillées](#consignes-remise).

Vous devez tout d'abord activer le dépôt du TP en suivant le lien qui vous a été transmis par Teams, puis former vos équipes sur GitHub de la même manière que pour le TP1.

## Fonctionnalités du script

Le script sert à afficher des blagues à partir de requêtes API seulement. Les blagues doivent provenir de l'API [**ChuckNorris.io**](https://api.chucknorris.io/). La documentation de l'API est indiquée sur la page principale. Voir en [annexe](#annexe) quelques exemples d'utilisation de l'API.

### Blague aléatoire

Lorsque le script est exécuté sans aucun paramètre, il affiche une blague au hasard. Son identifiant unique apparaît **à la fin** de la ligne, entouré de crochets.

```text
<texte de la blague> [<identifiant>]
```

<ConsoleWindow title="PowerShell" backgroundColor="#012456" noCopy="true" wrap="character">
```
PS C:\EspaceLabo> .\Get-ChuckNorrisJoke.ps1
Everyone wonders what caused the Big Bang. Chuck Norris. [BD9ZRRr6She8TI-H-F1yzA]
```
</ConsoleWindow>

### Blague spécifique

Lorsqu’on passe le numéro d’identification d’une blague dans le paramètre `-Id`, la blague correspondante est affichée.

L'affichage suit le même format que pour une blague aléatoire (E9).

<ConsoleWindow title="PowerShell" backgroundColor="#012456" noCopy="true" wrap="character">
```
PS C:\EspaceLabo> .\Get-ChuckNorrisJoke.ps1 -Id WZWE0JLbTh2_WaNB_P7arg
Chuck Norris once sawed a man in half..... With his beard. [WZWE0JLbTh2_WaNB_P7arg]
```
</ConsoleWindow>

### Filtrage par catégorie

Si on spécifie le paramètre `-Categorie` suivi du nom d’une catégorie valide, une blague au hasard est affichée, mais seulement dans cette catégorie. Cela limite les choix possibles.

L'affichage suit également le format E9.

<ConsoleWindow title="PowerShell" backgroundColor="#012456" noCopy="true" wrap="character">
```
PS C:\EspaceLabo> .\Get-ChuckNorrisJoke.ps1 -Categorie dev
Chuck Norris can compile syntax errors. [2c_aavbjsig1x1p6h8huuw]
```
</ConsoleWindow>

### Liste des catégories

On peut obtenir la liste des catégories valides en spécifiant le switch `-Liste`. Les catégories sont triées en **ordre alphabétique croissant** et affichées sous le titre `Catégories disponibles :`, avec le préfixe `- ` devant chacune.

La liste doit provenir de l'API; elle ne doit pas être inscrite directement dans le script.

<ConsoleWindow title="PowerShell" backgroundColor="#012456" noCopy="true" wrap="character">
```
PS C:\EspaceLabo> .\Get-ChuckNorrisJoke.ps1 -Liste
Catégories disponibles :
- animal
- career
- celebrity
- dev
(...)
```
</ConsoleWindow>

### Recherche de blague

On peut rechercher un mot-clé spécifique dans la base de données de blagues. En passant ce mot-clé par le paramètre `-Recherche`, on obtient toutes les blagues retournées par l'API pour cette recherche. L'en-tête reprend le mot-clé saisi et le nombre de résultats. La mention `résultat(s)` est conservée quel que soit le nombre.

```text
Recherche "<mot-clé>" : <N> résultat(s).
- <texte de la blague> [<identifiant>]
```

La dernière ligne est répétée pour chaque blague. Si la recherche ne donne aucun résultat, l'affichage est plutôt :

```text
Recherche "<mot-clé>" : 0 résultat(s).
Aucune blague trouvée.
```

L'absence de résultat est une situation valide, pas une erreur.

<ConsoleWindow title="PowerShell" backgroundColor="#012456" noCopy="true" wrap="character">
```text
PS C:\EspaceLabo> .\Get-ChuckNorrisJoke.ps1 -Recherche "electricity"
Recherche "electricity" : 4 résultat(s).
- Chuck Norris doesn't get shocked, the electricity gets Chuck Norris'd [xxLSn-EXSSSsmnpxFIhl_g]
- Chuck Norris is made of 94% perspiration, 4% electricity and 2% butterscotch ripple. [-JqN6AzxQGuKv0C0eI-xew]
- Ben Franklin discovered Electricity after Chuck Norris tolf him to "Go fly a Kite!" [o3U3rm7jQtml3Q0uY4OX5g]
- Chuck Norris makes toast in the shower, while using his hairdryer. As a result, his electricity bill is outrageous, so he doesn't pay it. [cRuxHMt_QUS0Cf69-tTd9A]

PS C:\EspaceLabo> .\Get-ChuckNorrisJoke.ps1 -Recherche "patate"
Recherche "patate" : 0 résultat(s).
Aucune blague trouvée.
```
</ConsoleWindow>

### Rapports d'erreurs

Si on spécifie un identifiant ou une catégorie erronée, on doit recevoir une erreur claire dans le *error stream*.

Le message doit contenir `Blague introuvable` ou `Catégorie introuvable`, selon le cas. La décision de lancer l'erreur doit découler de la réponse de l'API. Un texte simplement écrit en rouge ne constitue pas une erreur PowerShell; il faut l'envoyer avec `Write-Error`.

## Stratégie et plan de test

Vous devez élaborer votre plan dans **`plan-de-test.md`**, comme dans l'[exercice d'assurance-qualité](../exercices/20-tests.md). Vous pouvez partir du modèle Markdown `plan-de-test.md` inclus dans le dépôt de départ.

Pour ce travail, il faut seulement concevoir **les cas de tests**. L'exécution du plan de test, le journal d'exécution, le registre des défauts et les préconditions ne font pas partie des artéfacts à remettre dans le cadre de ce TP.

### Exigences fonctionnelles

Voici les exigences fonctionnelles à vérifier dans votre plan de test:

| ID | Le script doit... |
| --- | :-- |
| **E01** | Sans paramètre, afficher une seule blague aléatoire obtenue de l'API. |
| **E02** | Avec `-Id`, afficher la blague correspondant à l'identifiant fourni. |
| **E03** | Avec `-Categorie`, afficher une seule blague aléatoire appartenant à la catégorie fournie. |
| **E04** | Avec le switch `-Liste`, afficher `Catégories disponibles :`, puis toutes les catégories retournées par l'API en ordre alphabétique croissant, une par ligne précédée de puces `- `. |
| **E05** | Avec `-Recherche`, afficher l'en-tête `Recherche "<mot-clé>" : <N> résultat(s).`, puis toutes les blagues retournées par l'API pour cette recherche, une par ligne précédée de puces `- `. Le nombre annoncé doit correspondre au nombre de blagues affichées. |
| **E06** | Si une recherche ne donne aucun résultat, afficher l'en-tête avec le nombre `0`, puis `Aucune blague trouvée.`, sans lancer d'erreur. |
| **E07** | Si l'identifiant est introuvable avec l'option `-Id`, émettre une véritable erreur contenant `Blague introuvable`, sans afficher de blague. |
| **E08** | Si la catégorie est introuvable avec l'option `-Categorie`, émettre une véritable erreur contenant `Catégorie introuvable`, sans afficher de blague. |
| **E09** | Chaque fois qu'une blague est affichée, elle doit être suivie par son identifiant entre chochets carrés. |
| **E10** | Pour les appels valides, afficher uniquement les éléments demandés, sans erreur ni objet résiduel. |

Dans les formats ci-dessus, les éléments entre chevrons sont à remplacer par les valeurs réelles. Les fonctionnalités et les exemples suivants précisent ces exigences.

### Concevoir les cas de test

Rédigez **plusieurs cas distincts**, identifiés `T01`, `T02`, etc. C'est à vous de choisir les scénarios et les données. Votre ensemble doit couvrir **E01 à E10**, avec des cas usuels, des cas limites, des erreurs attendues et au moins un scénario d'intégration qui enchaîne plusieurs usages du script.

Pour chaque cas, indiquez les exigences visées, la catégorie du cas, la procédure et le résultat attendu. Remplissez aussi un tableau de couverture qui relie chaque exigence à ses cas de test. Écrivez les résultats attendus **avant l'essai**, à partir des exigences.

La procédure doit permettre à une autre personne de reproduire l'essai : décrivez les commandes à exécuter et les vérifications à faire **dans la perspective d'un utilisateur-testeur**. Les résultats attendus doivent préciser le nombre de blagues, le format, les valeurs vérifiables, l'ordre lorsqu'il est imposé et les diagnostics attendus.

:::warning
Les essais portent sur le **comportement observable** du script. Les commandes qui servent à lancer le script ou à vérifier une réponse de référence de l'API ont leur place dans le plan, mais pas les lignes de code de votre script.
:::
